| Containment | A person approves every action, including `block_ioc` and `purge_email`, which is stricter than section 4 of the policy. OT actions are never proposed | Proposed |
| Prompt budget | 75,000 characters, about 60,000 of them for data (v7), because the UAB's `ornith` takes 262,144 tokens. It was 29,000 and 14,000, set for Gemini's free tier, which cut rows from 54 of the 80 practice alerts (17 at the new size, `scripts/rows_cut.py`). Don't search on IPs shared by many identities. Data sends rows most important first: linked events, then changes of state, then repeats as counts (analysis section 5) | Proposed |
| JSON mode | Since v8, ask `ornith` without the server's JSON mode (`LLM_JSON_MODE=1` turns it back on). With reasoning on, JSON mode often answered only `{}` after a complete reasoning, which cost a whole retry. Code still checks the object, and takes it from between the first `{` and the last `}` if the model wraps it in text. Night of 8 Nov, `docs/agent_versions.md` | Proposed |
| Phishing campaign context | Since v8, for `UC-EML-001` to `003`, code adds the rest of the campaign (`AGENT_CAMPAIGN=0` turns it off): other copies from the same sender (who got it, no body), visits to the hosts of the reported email's links, sign-ins from the IPs that served them, and clicks on the same links. Exact-match searches only, and a search with more than 60 rows is dropped as a busy IP. This is level 1 seeing what level 2 grouping saw | Proposed |
| Incomplete evidence | A truncated search or rows cut from the prompt can't support the −1, and the ticket says the evidence is incomplete (analysis section 4) | Proposed |
| Closing without data | A `false_positive` with no log rows, or a `high` or `critical` one citing no event, becomes `needs_more_info` and goes to a person, because the alert's own text can be written by an attacker | Proposed |
| Alerts in other formats | Other field names and wrappers are accepted, gaps are filled from Deloitte's rule catalogue, and the ticket lists every assumption. Original fields are kept | Proposed |
| Grouping (level 2) | Plain code links alerts by exact identifiers only: account, host, session, message, sender, mail domain, file hash, outside IP, domain, customer, cloud identity or event. Two escalated alerts may link by anything they share, but by account or host only within 14 days. A closed alert joins an escalated one only by a specific identifier. Two closed true positives link by a specific identifier within 14 days. False positives and authorised alerts never link to each other, and are counted instead. An identifier in more than 25 alerts of the history links nothing. An incident takes its highest severity, and escalates as a chain when it holds a true positive and at least two rules | Proposed |
| Containment (level 4) | The LLM only writes suggestions. Plain code maps them onto the mock's 7 actions, takes targets from the CMDB, the directory or the alert, and sets approvers from section 4 of the policy: the SOC analyst for `block_ioc` and `purge_email`, N2 for accounts, keys and laptops, N2 plus the service owner for servers, and N2 plus the business for tills and web front ends. Each role needs a different person, an approval runs once, and OT, internal or shared IPs and our own domain are never proposed. Approvers are named but not authenticated: the console is local only | Proposed |
| Data leakage | ID numbers are only citation handles: no code, prompt, rule, test selection, label or score uses them as a signal. Prompts stay general and use no alert from the data as an example. Labels are written without seeing the agent's answer | Proposed |
| Held-out incident | The stolen cloud key case: `ALR-20261015-011819`, `ALR-20261015-011820` and `ALR-20261016-011821`, the last of which is in the development sample. Also `ALR-20261013-011901` until someone checks the link. Leave them out while tuning, and don't call it blind: the analysis has read them | Proposed |
| Investigation (level 3) | Plain code gathers the evidence of an escalated ticket or incident: every alert's linked events by ID, then every entity searched from 7 days before the first event to 1 day after the last, then two rounds of expansion by session and message ID from the attack's own rows. Repeats of one action are sent once with every event ID, attack rows before routine ones. The LLM, with reasoning on (`REPORT_ENABLE_THINKING`, default true), writes the analysis and picks the timeline's events. Code keeps only events it retrieved, takes each time from the log row, sorts by event time and adds any alert-linked event the LLM left out, folded per alert and log and marked as added by code. People's roles come from the directory, never the LLM, and event IDs in free text that were never retrieved are flagged (`src/agent/investigate.py`, run with `scripts/investigate.py`) | Proposed |
| Containment in reports | The LLM proposes steps from the mock's 7 actions with a target found in the retrieved data. The caller's policy check (`check_step` in `src/policy/containment.py`, the same rules as level 4 tickets) canonicalises the target, refuses OT, internal or shared IPs, our own domains and anything that isn't an indicator, and names the approvers. `src/agent/` never imports the containment rules. In the app each step becomes an `ActionProposal`, checked again, and goes through the same approve, reject and execute routes as a ticket's, keyed by the report's incident or ticket | Proposed |
| Related incidents | Plain code lists other alerts sharing a specific identifier (IP, domain, sender, message, session, file, cloud identity, event) as related. Same account or machine alone is a lead, never proof. With none, the report says there is no evidence of a link | Proposed |
| Human in the loop, levels 1-3 | Off by default: `AUTO_TRIAGE=0` is a master switch, and the queue works by clicking as before. With `AUTO_TRIAGE=1` a worker (`src/app/worker.py`) runs the fixed rules, then the LLM by rule severity, then criticality, then earliest deadline, through the same `work()` as a click. It groups by itself, at most once every `AUTO_GROUP_SECONDS`. With `AUTO_INVESTIGATE=1` it also writes reports for escalations, critical first, from the same LLM budget. Automatic: starting triage, grouping and investigation, and closing a ticket without review when `src/policy/auto_close.py` finds every condition met: code already closed it, final severity informational or low, verdict not `needs_more_info`, no policy or injection flags, evidence and authorisation checks passed, nothing on the OT network, and a run the worker started on the real agent. Human: every other ticket, every escalation, every `needs_more_info`, injection flag and OT alert, and all of level 4. `block_ioc` and `purge_email` keep their analyst approval, which is deliberately stricter than section 4 of the policy. The close and escalate logic didn't change, only who must look at the result. A person can reopen any auto-closed ticket. An auto-closed alert that joins an escalated incident goes back to a person by itself, because the policy escalates a chain even if each alert is low. `AUTO_CLOSE_SAMPLE_PERCENT` of auto-closes (5 by default) are shown at random for review, with counts per rule. Risks: an auto-close can hide a rule mistake or a model misled by planted text, and it isn't reviewed unless sampled. Evidence that was truncated doesn't stop an auto-close, because the fixed rules already accept it where it doesn't affect them. The LLM budget caps coverage: what doesn't fit stays for a person. | Proposed |
| SLA tracking | Targets live once in `src/policy/sla.py`, from section 3 of the policy, and the API serves them to the UI. The clock starts when an alert enters the store, not at its timestamp in the data, because imported alerts are historical. It stops when the triage ticket is created. A fallback ticket doesn't stop it, because nothing was triaged, so that clock runs until a real ticket or a person's decision. A higher final severity recalculates the deadline from the same start, and a lower one keeps the deadline already set. Informational has a daily batch and no invented time, so it has no deadline. Under 25% of the time left, or with the worker not running, an open alert is at risk. Delay never closes anything. Notifications stay in the app: critical to the SOC lead and CISO, high to the SOC lead, once at the rule's severity on entry, again if the final severity rises, and again on a breach. A person confirms the N2 call or handover. Limits: the SLA is measured in the app, not from the real SIEM arrival time. Nothing reaches the SOC lead, the CISO or on-call N2 outside the console, so a breach at night goes unseen until someone opens it. | Proposed |
